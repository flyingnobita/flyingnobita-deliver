## Corrections

1. **Orca setup request.** The Orca section told the user to run `/deliver-setup` and
   then "Ask setup: …". Codex has no slash command for a skill and selects it from a
   plain request, which the Herdr walkthrough already recorded in DLV-10. The section now
   names the skill and the settings in one request, matching the Herdr wording:

   ```text
   Run the deliver-setup skill: use Codex for planner, implementer, reviewer and QA, with one model available to my account. Validate all four profiles. Set max_workers = 1 and landing = "leave".
   ```

2. **Caller preflight crashed on Orca 1.4.256.**
   `orchestration run-current --json` omits `_meta`, while
   `deliver-orca-preflight.py` indexed `run_current['_meta']['runtimeId']`. Every Codex
   caller therefore failed with `{"orca": "broken", "error": "'_meta'"}`. The script now
   accepts a response without runtime metadata and still rejects a mismatched runtime;
   `test_run_current_without_runtime_meta_is_accepted` covers the current shape.

3. **`--retry-request` contract.** The adapter told workers to pass a delivery request ID
   to `worker-start --retry-request` on every new start. Orca accepts only the native
   request UUID it reported for the original request, and only to replay that request, so
   the first planner smoke was rejected before dispatch. The start and follow-up rows now
   omit the flag, and the evidence steps state that the delivery `request_id` is not a
   native UUID.

After these fixes, the affected setup step was rerun: the four smokes passed and the
configuration committed. The coordinator's explicit smoke and the delivery's
implementer/reviewer roles also used the documented Codex profile.

The rerun used the fixed preflight copied into the disposable worktree's installed skill;
that copy was not committed there. The committed branch is covered by the unit test, not
by a second install from this branch.

## Known limits and deviations

- The coordinator was this Orca chat session on the OpenCode harness, not the Codex
  orchestrator the Quick start describes. `deliver-orca-preflight.py` reports
  `{"orca": "broken", "error": "missing or ambiguous nested harness ancestry"}` here,
  which matches the README's limit of Claude Code, Codex and Antigravity as Orca
  orchestrators. This is an environment limit, not a documentation defect.
- The delivery was coordinated directly through Orca Tasks and Workers. The `deliver`
  skill's run record, intent/receipt and gate helpers were not produced for the delivery,
  so that part validates the Orca profile path and the first-delivery shape, not the full
  Deliver runtime. The setup run did produce its setup record and intent/receipt evidence.
- The global `-g` install path was not exercised; the live install was left alone. The
  installed suite at project scope is byte-identical to `a87f495`, and `codex exec` in a
  directory without project skills listed `deliver`, `deliver-review` and
  `deliver-setup`, confirming Codex sees the host's global install.
- `orca worktree create` needs the repository registered with Orca first. Opening the
  repository in the app does that; the CLI-only walkthrough required `orca repo add
  --path ...` before the first worktree could be created.
- Inherited model and effort are not expanded in launch receipts. The managed default was
  observed as `gpt-6.1-sol` / `medium`; exact per-launch effort is unverified.
- Only Orca 1.4.256 was exercised; flags and receipt fields may differ in other versions.
